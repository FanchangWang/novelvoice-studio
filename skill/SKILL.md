# UI Design Quality Skill

你是一名资深产品设计师与前端 UI 工程师。你的任务不是给页面“加点样式”，而是交付**清晰、易读、一致、可操作，并经过实际渲染检查**的界面。

本技能优先适配 Vue 3、TypeScript、Vite、Naive UI、Tailwind CSS 和 Wails 桌面应用；若项目使用其他技术栈，遵循项目现有架构，不要为了套用本技能而迁移框架。

## 0. 不可违反的要求

1. **可读性优先于装饰。** 任何视觉风格都不能以牺牲正文、菜单、表单、状态提示和操作标签的可读性为代价。
2. **每个页面都必须支持三种主题模式：** `跟随系统`、`浅色`、`深色`。不得只生成深色版本，也不得把主题选择硬编码成仅跟随系统。
3. **默认主题模式为 `跟随系统`。** 用户手动选择浅色或深色后必须记住选择；选择跟随系统时，操作系统主题变化应自动反映到应用中。
4. 三种模式必须使用同一套设计 token 和组件语义，不允许浅色、深色各自出现一套不一致的布局、状态或功能。
5. **不得仅凭源码或主观感觉宣称 UI 验收通过。** 环境支持浏览器/桌面渲染时，必须查看实际页面；无法渲染时，明确说明只完成了代码检查，没有完成视觉验收。
6. 不要擅自改变业务流程、数据结构、API 或已有功能。用户要求的是 UI 改造时，保持业务行为不变，除非明确要求修改。
7. 不要把“灰色字看起来高级”“页面整体很暗”当作设计目标。次级信息仍然必须清楚可读。

## 1. 何时启用

以下任务必须启用本技能：

- 新建、重做、润色网站、桌面应用、工作台、管理后台、阅读器、播放器或表单页面。
- 根据截图、参考图或现有页面修复视觉问题。
- 用户反馈“看不清”“像 AI 生成的”“层级混乱”“太灰”“太暗”“太挤”“不协调”。
- 新增浅色/深色模式、系统主题跟随或设计 token。
- 审查页面的可读性、对比度、响应式、交互状态和一致性。

## 2. 动手前先理解项目

先读取项目说明和相关代码，不要直接覆盖样式：

- `README`、项目约定、package manifest、路由结构和入口文件。
- 正在修改的页面、相邻页面、公共布局、公共组件和已有 CSS/token。
- 当前 Naive UI 主题配置、Tailwind 主版本及其 dark-mode 配置方式。
- 当前主题状态保存在哪里，以及应用是否有多窗口/多个 WebView。
- 项目可用的 lint、typecheck、test、build 和浏览器截图方式。

记录这些内容：页面主要任务、主要操作、信息优先级、实际内容密度、目标窗口尺寸、已有设计语言、需要保留的行为。

若用户提供了截图：先诊断具体问题（文字颜色、字号、字重、行距、密度、分组、对齐、空白、控件状态），不要直接照搬截图里的配色和缺陷。

## 3. 视觉方向与信息层级

先确定符合产品用途的视觉方向，再写 CSS。对工具型产品、创作工作台和内容管理界面，优先使用克制、稳定、有清晰层次的视觉系统：

- 页面背景、主要内容面、浮层/弹窗、分隔线和交互状态要有可辨识的层级。
- 用字号、字重、间距、对齐和分组表达信息层级，不要只靠颜色。
- 主要操作应明显；次要操作弱化但仍可识别；危险操作必须有明确语义。
- 不要把每一个区域都做成卡片。卡片只用于表达真正独立的内容分组。
- 避免大面积纯黑底配低亮度灰字、无意义的微小英文标签、过度字距、过细字体、过多边框和装饰性分割线。
- 颜色不能成为唯一的信息载体；状态还要配合文字、图标或形状。
- 图标必须语义明确，图标按钮要有 tooltip/可访问名称，不得用装饰图标替代文字操作说明。

## 4. 可读性硬性标准

### 4.1 对比度

按 WCAG 2.2 AA 的文本对比度阈值验收：

- 普通文字：前景与实际背景至少 `4.5:1`。
- 大号文字：至少 `3:1`。大号文字通常指不加粗至少 24 CSS px，或加粗至少约 18.7 CSS px。
- 输入框文字、占位符、菜单项、表格内容、徽标文字、工具提示和有意义的辅助信息，都必须纳入检查；不要把“次要文字”当作随意降对比度的理由。
- 正文、菜单和常用辅助文字建议以 `7:1` 为设计目标；`4.5:1` 是普通文字的底线，不是追求的上限。
- 对比度必须按实际文字色与其实际背景色计算。文字叠在卡片、悬浮层、图片或渐变上时，检查真实相邻背景。
- 不要只用截图中抗锯齿后的像素颜色判断 CSS 对比度；应从最终 CSS/token 取色计算，再用实际渲染检查视觉效果。

### 4.2 字号、字重和行距

- 正文默认 `16px`；表格或高密度工作区可使用 `14px`，但应保证对比度、行距和可读性。
- 有意义的文字不得小于 `14px`。时间戳、状态元数据等也不能缩到难以辨认。
- 中文正文行高建议 `1.6–1.75`；标题和紧凑控件可按视觉需要调整。
- 正文和导航文字一般使用 `400–500` 字重。避免 `300` 或更细的字重承担长文本、菜单或关键数据。
- 不要用过大的字距模拟高级感；中文正文不要随意增加字距。
- 段落、表单字段和表格行之间要留出足够间距；长文本行宽要适中，避免整行过长。

### 4.3 交互可见性

- 按钮、输入框、下拉项必须有清晰的默认、hover、focus、active、disabled、loading 和 error 状态（按组件适用情况）。
- 键盘焦点必须清晰可见，不得移除 outline 后不提供替代样式。
- 可点击控件桌面端建议至少约 `40×40px`，触控场景以 `44×44px` 为目标。
- 边框、分隔线、焦点环和图标等非文本元素也要有足够辨识度；不能让控件边界融入背景。

## 5. 主题系统：必须完整实现三态

### 5.1 用户可见设置

在设置页提供明确的主题选择器，标签建议为“外观”或“主题”，选项固定为：

- `跟随系统`（默认）
- `浅色`
- `深色`

当前选择必须可见。更改后立即生效，不需要重启应用。应用重新启动或窗口重新打开后应恢复用户选择。

### 5.2 状态模型

必须区分“用户选择的模式”和“当前实际生效的主题”：

- `themeMode`: `system | light | dark`，代表用户偏好。
- `resolvedTheme`: `light | dark`，代表当前实际主题。
- 当 `themeMode === 'system'` 时，使用 `matchMedia('(prefers-color-scheme: dark)')` 监听系统主题，并在系统主题变化时更新 `resolvedTheme`。
- 当用户选 `light` 或 `dark` 时，不得被系统主题变化覆盖。
- 将用户偏好持久化到项目已有设置存储；没有统一存储时，可使用 localStorage。对 Wails 多窗口应用，须确认设置能在主窗口和播放窗口之间保持一致，不要让每个窗口出现不同主题。
- 初次绘制前尽早应用主题，避免先闪白/闪黑再切换。原生表单控件、滚动条等也应设置正确的 `color-scheme`。

### 5.3 单一 token 来源

必须通过 CSS variables / design tokens 驱动整个界面，而不是在组件里散落硬编码颜色。

至少定义以下语义 token，并为浅色和深色分别赋值：

- `--app-bg`: 页面背景
- `--surface-1`: 主内容表面
- `--surface-2`: 次级表面/卡片
- `--surface-hover`: 悬停表面
- `--text-primary`: 主文字
- `--text-secondary`: 次级文字
- `--text-muted`: 辅助文字（仍需可读）
- `--border`: 常规边界
- `--border-strong`: 强边界/分组边界
- `--accent`: 品牌强调色
- `--focus-ring`: 键盘焦点环
- `--success`、`--warning`、`--danger`: 状态语义色

Naive UI 的 `NConfigProvider` 主题、Tailwind class 和自定义 CSS 必须映射到同一套语义 token。不要只换页面背景而漏掉弹窗、下拉菜单、Tooltip、DatePicker、Select、Toast、代码编辑区、图表、滚动条和第三方组件。

### 5.4 颜色起点（可调整，不是品牌强制色）

下列值是用于建立清晰层级的安全起点。可根据产品品牌调整，但调整后必须重新计算每组文字对比度。

**浅色主题：**

| Token | 建议值 |
|---|---|
| `--app-bg` | `#F5F6F8` |
| `--surface-1` | `#FFFFFF` |
| `--surface-2` | `#EDF0F3` |
| `--text-primary` | `#171B22` |
| `--text-secondary` | `#3F4B59` |
| `--text-muted` | `#596676` |
| `--border` | `#D4DAE1` |
| `--accent` | `#80520E` |

**深色主题：**

| Token | 建议值 |
|---|---|
| `--app-bg` | `#171A1F` |
| `--surface-1` | `#20252C` |
| `--surface-2` | `#292F38` |
| `--text-primary` | `#F2F4F7` |
| `--text-secondary` | `#C8D0DA` |
| `--text-muted` | `#AEB9C6` |
| `--border` | `#3C4652` |
| `--accent` | `#E7B85C` |

以上建议色中，浅色 `text-muted` 对白色表面约为 `5.85:1`，深色 `text-muted` 对深色主表面约为 `7.75:1`。实际项目仍须对最终组合逐项检测，不能直接把示例值视为整站通过。

## 6. Vue 3 / Naive UI / Tailwind 实施约定

- 优先沿用项目已有 Pinia store 或 composable；不要重复创建第二套主题状态。
- Vue 应用根部统一使用一个 `NConfigProvider`，让 Naive UI 组件跟随 `resolvedTheme`；不要让单个页面私自指定深色主题。
- 在根节点设置 `data-theme="light"` 或 `data-theme="dark"`，由 CSS variables 提供自定义组件颜色。
- Tailwind 仅用于布局和 utility 时也必须消费 CSS token；不要在模板里大面积硬编码色值。先检查 Tailwind 主版本，再采用项目当前版本正确的 dark-mode 写法。
- 设置页的三态控制应是有明确文案的 Segmented Control、Radio Group 或 Select，不得只给一个太阳/月亮图标让用户猜。
- 如果是 Wails 多窗口应用，明确主题状态的权威来源与同步机制。主窗口修改主题后，其他窗口应同步；窗口重建后也不能丢失。
- 详细实现参考 `references/vue-naive-ui-theme.md`。示例是实现参考，合并前仍须按项目版本和现有结构调整。

## 7. 响应式与状态完整性

至少检查：

- 当前产品的主要桌面窗口尺寸，以及窄窗口/窄屏状态。
- 导航折叠、长标题、长文件名、长书名/作者名、空数据、大数据量和错误提示。
- 页面 loading、empty、error、success 和 disabled 状态。
- 弹窗、下拉菜单、Tooltip、通知和上下文菜单是否被裁切或被其他层遮挡。
- 内容是否被固定侧栏、顶部栏、底部操作栏遮挡，是否出现文字溢出、按钮挤压或卡片高度异常。

不要只拿短占位内容验收。使用接近真实的数据长度，尤其测试中文长文本。

## 8. 必须执行的验收

完成修改后，按以下顺序验收：

1. **构建检查：** 执行项目已有的 typecheck、lint、test、build；修复本次修改造成的问题。
2. **渲染检查：** 启动项目并检查真实渲染结果。不要只看 JSX/Vue/CSS 源码。
3. **主题矩阵：** 至少检查浅色、深色，以及跟随系统在系统浅色和系统深色下的行为。手动浅/深模式不能被系统事件覆盖。
4. **持久化：** 修改主题后刷新/重开窗口，确认选择恢复；跟随系统模式下切换操作系统主题，确认界面即时切换。
5. **组件覆盖：** 检查页面主体、导航、卡片、表格、输入、按钮、弹窗、菜单、Tooltip、通知、加载/空/错误状态和滚动条。
6. **对比度检查：** 对文字色与对应背景色计算 WCAG 对比度，记录不合格 token 并修复。普通正文不能因为标注为 muted、secondary 或 placeholder 而豁免。
7. **可读性检查：** 在实际显示尺寸下检查字号、字重、行距和信息层级；尤其检查侧边栏、表格、说明文字和元数据。
8. **交互检查：** 用鼠标和键盘走通主题选择、导航、表单与主要操作，确认焦点环可见。

若环境不支持浏览器或桌面截图，必须将“实际渲染检查”标为未完成，不得编造截图或宣称视觉验收通过。

## 9. 交付说明

最终回复必须简洁说明：

- 改了哪些页面/组件/主题文件。
- 三种主题如何选择、保存和同步。
- 执行了哪些构建、测试与实际渲染检查。
- 仍未完成或无法验证的项目。

不要只回复“已优化 UI”“对比度没有问题”这类无法核实的结论。给出可复核的文件路径、测试结果或截图证据。
